# ระบบตรวจสอบความพร้อมของสินค้าคงเหลือแยกตามสาขา BaanDee
**BaanDee Branch Stock Readiness**

## 1. ภาพรวมโครงงาน

โครงงานนี้พัฒนาต้นแบบผลิตภัณฑ์ข้อมูล (Data Product Prototype) สำหรับตรวจสอบความพร้อมของสินค้าคงเหลือแยกตามสาขา โดยใช้ Python และ Streamlit ในการพัฒนาเว็บไซต์ เพื่อช่วยให้ผู้ใช้สามารถตรวจสอบข้อมูลสินค้าและสถานะความพร้อมจำหน่ายได้สะดวกขึ้น

ผู้ใช้สามารถเลือกสาขา ค้นหาและกรองรายการสินค้า ตรวจสอบจำนวนสินค้าคงเหลือและจุดสั่งเติม บันทึกหรือแก้ไขหมายเหตุประกอบการตรวจสอบ และดาวน์โหลดข้อมูลเป็นไฟล์ CSV ได้ นอกจากนี้ยังมี API จำลองสำหรับสาธิตการตรวจสอบคำสั่งซื้อและการจัดการกรณีที่ API ไม่สามารถให้บริการได้

**ข้อจำกัดสำคัญ:** โครงงานนี้เป็นต้นแบบเพื่อการศึกษา ข้อมูลสินค้าคงเหลือเป็นข้อมูลจำลอง ไม่ใช่ข้อมูลสต็อกจริงของ BaanDee และ API ที่ใช้เป็น API จำลองซึ่งไม่ได้รับการยืนยันว่าเชื่อมต่อกับระบบอย่างเป็นทางการของ BaanDee

## 2. วัตถุประสงค์

1. พัฒนาต้นแบบเว็บไซต์สำหรับตรวจสอบความพร้อมของสินค้าคงเหลือแยกตามสาขา
2. นำกระบวนการตรวจสอบและจัดการคุณภาพข้อมูลมาใช้กับชุดข้อมูลสินค้าและสต็อก
3. แสดงผลข้อมูลด้วยตัวกรองและสถานะที่เข้าใจง่าย
4. สาธิตการเชื่อมต่อระหว่างเว็บไซต์กับ API จำลอง
5. รองรับการบันทึกหมายเหตุ การแก้ไขข้อมูลประกอบ และการส่งออกผลลัพธ์เพื่อใช้ตรวจสอบเพิ่มเติม

## 3. แหล่งข้อมูลและข้อจำกัด

โครงงานประกอบด้วยข้อมูลที่ใช้ในการสาธิต ดังนี้

- **ข้อมูลต้นฉบับ:** ข้อมูลที่เก็บไว้เพื่อใช้เป็นจุดเริ่มต้นของกระบวนการเตรียมข้อมูล
- **ข้อมูลจำลอง:** ข้อมูลสินค้าและจำนวนสินค้าคงเหลือของแต่ละสาขาที่สร้างขึ้นเพื่อใช้ทดสอบระบบ
- **ข้อมูลที่ผ่านการทำความสะอาด:** ข้อมูลที่ผ่านกระบวนการตรวจสอบและจัดการตามกฎที่กำหนดไว้
- **ข้อมูลที่ต้องตรวจสอบเพิ่มเติม:** ข้อมูลที่พบปัญหาและถูกแยกไว้เพื่อไม่ให้นำไปรวมกับข้อมูลสะอาดโดยไม่มีการตรวจสอบ
- **API จำลอง:** ใช้สาธิตการตรวจสอบคำสั่งซื้อ ข้อมูลสินค้า และรายการแจ้งปัญหา

ข้อมูลทั้งหมดใช้เพื่อการศึกษาและการสาธิตการทำงานของต้นแบบเท่านั้น ไม่ควรนำไปใช้ตัดสินใจเกี่ยวกับสต็อกจริงโดยไม่มีการตรวจสอบกับแหล่งข้อมูลที่เชื่อถือได้

## 4. หลักเกณฑ์การแสดงสถานะสินค้า

ระบบกำหนดสถานะสินค้าโดยพิจารณาจากจำนวนสินค้าคงเหลือและจุดสั่งเติม ดังนี้

| เงื่อนไข | สถานะ |
|---|---|
| จำนวนสินค้าคงเหลือเท่ากับ 0 | หมดสต็อก |
| จำนวนสินค้าคงเหลือมากกว่า 0 และไม่เกินจุดสั่งเติม | ใกล้หมด |
| จำนวนสินค้าคงเหลือมากกว่าจุดสั่งเติม | พร้อมจำหน่าย |

หลักเกณฑ์ข้างต้นเป็นกฎที่กำหนดขึ้นสำหรับต้นแบบนี้ ไม่ใช่นโยบายการจัดการสินค้าคงเหลือที่ได้รับการยืนยันจาก BaanDee

## 5. ความสามารถของระบบ

### 5.1 การตรวจสอบสินค้าตามสาขา
- เลือกสาขาที่ต้องการตรวจสอบ
- ค้นหาสินค้าจากข้อมูลที่ระบบรองรับ
- กรองรายการตามสถานะความพร้อมของสินค้า
- ตรวจสอบจำนวนสินค้าคงเหลือและจุดสั่งเติม
- แสดงข้อมูลอ้างอิงเวลาของชุดข้อมูลที่ใช้ตรวจสอบ

### 5.2 การจัดการหมายเหตุ
- เพิ่มหมายเหตุประกอบการตรวจสอบสินค้า
- แก้ไขหมายเหตุที่บันทึกไว้
- เรียกดูหมายเหตุเดิมเพื่อใช้ประกอบการตรวจสอบ

หมายเหตุถูกจัดเก็บในไฟล์ CSV ตามการออกแบบของต้นแบบ การคงอยู่ของข้อมูลหลังรีเฟรชหน้าเว็บไม่ได้รับประกันว่าจะคงอยู่หลังการรีสตาร์ตหรือการปรับใช้แอปพลิเคชันใหม่

### 5.3 การส่งออกข้อมูล
- ดาวน์โหลดผลการค้นหาหรือข้อมูลที่แสดงในระบบเป็นไฟล์ CSV
- นำข้อมูลที่ดาวน์โหลดไปตรวจสอบหรือวิเคราะห์เพิ่มเติมได้

### 5.4 การเชื่อมต่อ API จำลอง
- ตรวจสอบสถานะการให้บริการผ่านเส้นทาง `/health`
- สาธิตการค้นหาข้อมูลคำสั่งซื้อ
- แสดงผลเมื่อพบข้อมูลหรือไม่พบข้อมูล
- แสดงข้อความเมื่อไม่สามารถเชื่อมต่อ API ได้

ความสามารถที่ใช้งานได้จริงขึ้นอยู่กับโค้ดเวอร์ชันที่เผยแพร่และความพร้อมใช้งานของ API จำลอง

## 6. การจัดการคุณภาพข้อมูล

โครงงานใช้กระบวนการตรวจสอบคุณภาพข้อมูลก่อนนำข้อมูลไปแสดงในเว็บไซต์ โดยแยกข้อมูลออกเป็นข้อมูลต้นฉบับ ข้อมูลที่ผ่านการทำความสะอาด และข้อมูลที่ต้องตรวจสอบเพิ่มเติม

### 6.1 ผลสรุปการตรวจสอบข้อมูล

จากรายงาน `data/reports/branch_inventory_quality_report.csv` มีผลสรุปดังนี้

| รายการตรวจสอบ | ผลลัพธ์ |
|---|---:|
| จำนวนแถวข้อมูลดิบ | 329 |
| จำนวนแถวข้อมูลสะอาด | 326 |
| จำนวนแถวที่แยกกักไว้ตรวจสอบ | 3 |
| จำนวนสาขาในข้อมูลสะอาด | 4 |
| จำนวนสินค้าในข้อมูลสะอาด | 82 |
| คีย์สาขาและสินค้าที่ซ้ำคงเหลือ | 0 |
| จำนวนสต็อกติดลบที่เหลือ | 0 |
| วันที่ `as_of` ที่ขาดหายหลังทำความสะอาด | 0 |

### 6.2 ประเภทปัญหาคุณภาพข้อมูล

รายงาน `data/reports/branch_inventory_quality_issues.csv` ระบุปัญหาหลัก 3 ประเภท ได้แก่

1. **จำนวนสินค้าคงเหลือไม่ถูกต้องหรือติดลบ:** แยกข้อมูลไว้เพื่อตรวจสอบโดยผู้รับผิดชอบ แทนการเดาค่าที่ถูกต้องขึ้นมาเอง
2. **วันที่อ้างอิงข้อมูล (`as_of`) ขาดหายหรือไม่ถูกต้อง:** แยกข้อมูลไว้ตรวจสอบก่อนนำไปใช้
3. **รายการสาขาและสินค้าซ้ำกัน:** จัดการรายการซ้ำตามกฎที่กำหนด โดยเก็บรายการแรกไว้และแยกรายการซ้ำออก

### 6.3 การตรวจสอบย้อนกลับ

รายงานคุณภาพข้อมูล รายการปัญหาที่พบ และบันทึกการแก้ไขถูกจัดเก็บไว้ใน `data/reports/` เพื่อให้ตรวจสอบกระบวนการทำงานได้

- `branch_inventory_quality_report.csv` — สรุปผลการตรวจสอบคุณภาพข้อมูล
- `branch_inventory_quality_issues.csv` — รายการปัญหาที่ตรวจพบและวิธีจัดการ
- `correction_log.csv` — บันทึกการเปลี่ยนแปลงข้อมูลตามกระบวนการที่ใช้
- `test_results.csv` — สรุปผลการทดสอบระบบ

การแยกข้อมูลไว้ตรวจสอบไม่ได้หมายความว่าข้อมูลทุกแถวได้รับการแก้ไขแล้ว และการรายงานผลต้องอ้างอิงจากไฟล์ผลลัพธ์ของกระบวนการที่รันจริง

## 7. โครงสร้างโครงการ

โครงสร้างหลักของโครงการประกอบด้วย

- `src/app.py` — โปรแกรมเว็บไซต์ที่พัฒนาด้วย Streamlit
- `api/` — โปรแกรม API จำลอง
- `data/raw/` — ข้อมูลต้นฉบับ
- `data/generated/` — ข้อมูลจำลองที่สร้างขึ้นเพื่อการสาธิต
- `data/cleaned/` — ข้อมูลที่ผ่านการทำความสะอาดและเตรียมใช้งาน
- `data/quarantine/` — ข้อมูลที่แยกไว้เพื่อตรวจสอบเพิ่มเติม
- `data/reports/` — รายงานคุณภาพข้อมูล บันทึกการแก้ไข และผลการทดสอบ
- `tests/` — โปรแกรมและสคริปต์สำหรับทดสอบระบบ
- `requirements.txt` — รายการไลบรารีที่จำเป็น
- `.env.example` — ตัวอย่างการกำหนดค่าตัวแปรสภาพแวดล้อม
- `AI_USE.md` — รายละเอียดการใช้ AI ช่วยพัฒนาโครงงาน

## 8. วิธีติดตั้งและเรียกใช้งาน

### 8.1 เตรียมสภาพแวดล้อม

ติดตั้ง Python เวอร์ชันที่รองรับไลบรารีในโครงการ จากนั้นเปิดเทอร์มินัลในโฟลเดอร์หลักของโครงการ

### 8.2 ติดตั้งไลบรารี

```bash
pip install -r requirements.txt
```

### 8.3 เปิดเว็บไซต์

```bash
streamlit run src/app.py
```

จากนั้นเปิด URL ที่ Streamlit แสดงในเทอร์มินัล

### 8.4 ตั้งค่า API จำลอง

กำหนดตัวแปร `BAANDEE_API_URL` ให้เป็น URL ของ API จำลองที่ใช้งานจริง โดยดูรูปแบบจาก `.env.example`

หากเผยแพร่เว็บไซต์ผ่าน Streamlit Community Cloud ให้กำหนดตัวแปรนี้ในส่วน Secrets ของแอปพลิเคชันตามรูปแบบที่โค้ดรองรับ

เว็บไซต์และ API จำลองเป็นบริการแยกกัน หาก API ไม่พร้อมใช้งาน ฟังก์ชันที่ต้องเรียก API อาจไม่สามารถทำงานได้ตามปกติ

## 9. ผลการทดสอบระบบ (Test Results)

ระบบมีกรณีทดสอบทั้งหมด 11 กรณี ตั้งแต่ T01–T11 ครอบคลุมการตรวจสอบข้อมูลสต็อก การค้นหาสินค้า การบันทึกหมายเหตุ การทำงานของ API และการจัดการข้อผิดพลาด

| Test ID | รายการทดสอบ | วิธีทดสอบ | ผลที่บันทึก |
|---|---|---|---|
| T01 | ตรวจสอบว่ามีไฟล์ข้อมูลพร้อมใช้งาน | Automated | PASS |
| T02 | ตรวจสอบว่าข้อมูลไม่ว่าง | Automated | PASS |
| T03 | ตรวจสอบจำนวนสต็อกติดลบหรือค่าที่ไม่ใช่ตัวเลข | Automated | PASS |
| T04 | ตรวจสอบคู่สาขาและสินค้าไม่ซ้ำ | Automated | PASS |
| T05 | ตรวจสอบสถานะสต็อกตามกฎที่กำหนด | Automated | PASS |
| T06 | ค้นหาสินค้าที่ไม่มีอยู่ | Manual | PASS |
| T07 | บันทึกและเรียกดูหมายเหตุ | Manual | PASS |
| T08 | เปลี่ยนสาขาและตรวจสอบข้อมูล | Manual | PASS |

**สรุปผล:** จากบันทึกการทดสอบที่จัดทำไว้ มีกรณีทดสอบ 11 กรณีที่ระบุผล PASS แบ่งเป็น Automated test 5 กรณี และ Manual test 6 กรณี

T01–T05 เป็นผลจากการทดสอบอัตโนมัติตามบันทึก ส่วน T06–T11 เป็นผลจากการทดสอบด้วยตนเองที่ผู้พัฒนารายงานไว้ใน `test_results.csv` ทั้งนี้ ผล PASS ในตารางอ้างอิงตามบันทึกการทดสอบ ไม่ได้หมายความว่าได้รันชุดทดสอบทั้งหมดซ้ำอีกครั้งก่อนเผยแพร่เวอร์ชันนี้แล้ว

ไฟล์หลักฐานผลทดสอบ: `data/reports/test_results.csv`

ข้อจำกัด: การทดสอบ API ใช้ Demo API และข้อมูลตัวอย่าง ไม่ใช่การเชื่อมต่อ API จริงของ BaanDee

## 10. ข้อจำกัดและแนวทางพัฒนาต่อ

1. ข้อมูลสต็อกเป็นข้อมูลจำลอง ไม่ใช่ข้อมูลปัจจุบันจากระบบ BaanDee
2. API เป็น API จำลองเพื่อการศึกษา ไม่ใช่ API อย่างเป็นทางการของ BaanDee
3. การจัดเก็บหมายเหตุในไฟล์ CSV ไม่เหมาะกับการใช้งานจริงที่มีผู้ใช้หลายคนพร้อมกัน และอาจไม่คงอยู่หลังการรีสตาร์ตหรือการปรับใช้แอปพลิเคชันใหม่
4. เวลาที่แสดงอ้างอิงจากข้อมูลที่บันทึกไว้ในชุดข้อมูล ไม่จำเป็นต้องเป็นเวลาปัจจุบัน
5. การเรียกใช้ API ขึ้นอยู่กับเครือข่ายและความพร้อมใช้งานของบริการ
6. ก่อนนำไปใช้จริง ควรเชื่อมต่อแหล่งข้อมูลที่ได้รับอนุญาต ใช้ฐานข้อมูลที่เหมาะสม และเพิ่มการควบคุมสิทธิ์กับการตรวจสอบความถูกต้องของข้อมูล

## 11. การใช้ปัญญาประดิษฐ์ช่วยพัฒนา

รายละเอียดการใช้เครื่องมือปัญญาประดิษฐ์ ขอบเขตการช่วยเหลือ และการตรวจสอบผลลัพธ์ระบุไว้ใน `AI_USE.md` โดยผู้พัฒนามีหน้าที่ตรวจสอบโค้ด ผลลัพธ์ และคำอธิบายทั้งหมดก่อนส่งงาน

## 12. สรุป

โครงงานนี้เป็นต้นแบบ Data Product สำหรับสาธิตการตรวจสอบความพร้อมของสินค้าคงเหลือแยกตามสาขา โดยผสานการแสดงผลข้อมูล การจัดการคุณภาพข้อมูล การบันทึกหมายเหตุ การส่งออกข้อมูล และการเชื่อมต่อ API จำลองเข้าด้วยกัน

ระบบมีวัตถุประสงค์เพื่อแสดงแนวทางการสร้างผลิตภัณฑ์ข้อมูลที่ตรวจสอบและสาธิตได้ ไม่ใช่ระบบบริหารสต็อกที่เชื่อมต่อกับข้อมูลจริงของ BaanDee
